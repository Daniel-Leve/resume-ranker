# Phase 3 Architecture — Semantic Candidate Reranking

## Overview

Phase 3 is a local Python pipeline that takes the initial shortlist of candidates generated by Phase 2 (Hybrid Retrieval) and semantically reranks them against the Job Description. It uses Voyage AI's powerful cross-encoder model (`rerank-2.5`) to evaluate the deep semantic relevance of each candidate's entire profile.

---

## Event Flow

```
Phase 2 Output
  outputs/<job-id>-retrieval.json
            │
            │  Extract candidate_ids
            ▼
    Python Rerank Worker
    (python -m phase3.rerank --job jobs/<job-id>.txt)
            │
            ├── 1. Load Job Description (.txt)
            │
            ├── 2. MongoDB Document Reconstruction
            │      For each candidate_id:
            │        - Fetch all chunks from candidate_chunks
            │        - Sort by chunk_index
            │        - Format with headers: "[EXPERIENCE]\n..."
            │        - Truncate at RERANK_MAX_DOCUMENT_CHARS
            │
            ├── 3. Voyage AI Cross-Encoder (rerank-2.5)
            │      Query: Job Description
            │      Documents: Array of Reconstructed Candidate Profiles
            │      - Evaluates the query and document jointly
            │      - Returns a relevance_score for each
            │
            ├── 4. Score Separation & Provenance
            │      - Assign rerank_rank (1 to N)
            │      - Calculate rank_change (Phase 2 rank - Phase 3 rank)
            │      - Preserve Phase 2 matched_chunks (retrieval evidence)
            │      - DO NOT blend hybrid_score with rerank_score
            │
            └── 5. Output Generation
                  │
                  ▼
     outputs/<job-id>-reranked.json
     outputs/<job-id>-rerank-evaluation.json
     (Consumed by Phase 4)
```

---

## Core Principle: Retrieve-then-Rerank

The AI resume screening system is designed across multiple phases to balance computational cost and search precision. 

1. **Phase 2 (Retrieval - Bi-encoders & BM25)**: Casts a wide, cheap net. It processes thousands of resumes in milliseconds via MongoDB Atlas to find an initial pool (e.g., top 15).
2. **Phase 3 (Reranking - Cross-encoders)**: Uses Voyage `rerank-2.5`. Cross-encoders evaluate the Job Description and the Resume *together* at the same time, allowing for deep reasoning about how the resume fulfills the job requirements. Because this is computationally expensive, Phase 3 applies this model *only* to the handful of top candidates identified by Phase 2.

---

## Document Reconstruction — Design Rationale

In Phase 2, resumes are heavily chunked (Skills, Experience, Education) to maximize BM25 keyword density and isolated vector relevance.

However, cross-encoders perform best when they have a holistic view of the person. A single "Skills" chunk does not tell the cross-encoder if those skills were used in the "Experience" chunk. Thus, Phase 3 relies on `document_builder.py` to:

1. **Query MongoDB**: Fetch all chunks belonging to the candidate.
2. **Order by `chunk_index`**: Ensure the resume reads top-to-bottom natively.
3. **Inject Section Headers**: Wrap chunks in labels (e.g., `[EXPERIENCE]`) to give the cross-encoder structural context.
4. **Enforce Token Ceilings**: Truncate at `RERANK_MAX_DOCUMENT_CHARS` (default: 30,000 chars) to prevent Voyage API token limit errors (16,000 tokens for `rerank-2.5`) if a candidate submits a 20-page resume.

---

## Scoring and Provenance

Phase 3 introduces `rerank_score` (a raw relevance score output by Voyage) and `rerank_rank`.

**Strict Score Separation:**
Crucially, Phase 3 **does not** blend or average the `rerank_score` with the Phase 2 `hybrid_score`. Blending a semantic cross-encoder score with an RRF score introduces statistical noise. Phase 3 acts as the final arbiter of rank.

**Provenance Preservation:**
Phase 2 provenance (BM25 rank, Vector rank, and specifically `matched_chunks`) is strictly preserved inside the Phase 3 output under a `phase2` dictionary block. 

This creates an auditable trail:
*   **Retrieval Evidence**: Phase 2 `matched_chunks` shows *how* the system found the candidate.
*   **Semantic Relevance**: Phase 3 `rerank_score` shows *why* the candidate is a strong fit.

---

## Phase 2 → Phase 3 Compatibility

| Phase 2 Field | Phase 3 Usage |
|---|---|
| `candidate_id` | Primary key to query MongoDB for full resume chunks. |
| `hybrid_score` | Preserved for auditing. Used to calculate initial order. |
| `retrieval` (lexical/vector rank) | Preserved for auditing. |
| `matched_chunks` | Preserved as undeniable retrieval evidence. |
| `source_key` | Passed through to Phase 3 output. |

Phase 2 JSON files and MongoDB collections are **read-only** during Phase 3. No Phase 2 data is altered or corrupted.

---

## Phase 4 Interface

The `outputs/<job-id>-reranked.json` file is Phase 4's input.

By providing Phase 4 with the final semantic `rerank_rank` AND the original Phase 2 `matched_chunks`, Phase 4 has everything it needs to generate transparent, trustworthy explainability text for the recruiter (e.g., *"This candidate ranked #1 because the reranker found high semantic overlap with the JD, and specifically matched their 'Experience' and 'Skills' sections during initial retrieval"*).
